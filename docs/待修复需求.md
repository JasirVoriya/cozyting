## 7. 第 1 层（Rust `core/`）公共逻辑下沉与跨端 FFI 解耦（减少 Android/iOS 重复造轮子）

| 字段 | 内容 |
|---|---|
| **用户期望** | 在“第 1 层 Rust 公共协议引擎 + 第 2/3 层由 Android 与 iOS 各自原生实现”的架构下，将当前散落在 Android Kotlin 层但与操作系统无关的业务逻辑尽量下沉到第 1 层 Rust `core/`，让未来 iOS 端只需实现系统抓音（ReplayKit/AudioToolbox）与 SwiftUI 渲染，避免在 Swift 侧重造一遍状态机与并发协调轮子 |
| **当前事实** | 目前多项平台无关逻辑仍写在 Android 侧：① `core/src/ffi.rs` 将 `Engine`（句柄表、AAC 喂入队列、停机防死锁、错误状态、`AUTH_MODE`）与 Android JNI 绑定在同一 `#[cfg(feature = "jni")] mod android` 内，尚未解耦为平台无关门面；② `CastService.kt`（L194–359）在 Kotlin 侧维护了一整套复杂的多箱并发协调状态机（`desiredReceivers`、`activeOrSubmittedReceivers`、`pendingReconcileIps`、`pendingSpeakerVolumes`、`pendingGroupVolume`、`inFlightAddIp`、`mergeConnectingReceivers`、`removeReceiverFromStatsJson`）；③ `CastRouteSelection.kt` 在 Kotlin 侧解析 6 列 TSV、`looksLikeTv()` 启发式判断、默认过滤未声明 MiPlay 节点、本地缓存与实时发现合并、本机/多音箱互斥路由状态机；④ `LatencyDisplay.kt` 与 `AuthModeResolve.kt` 在 Kotlin 侧二次解析 `stats` JSON 判定 `Hidden`/`Loading`/`Value(ms)` 与认证模式映射 |
| **下沉范围与分层边界** | **建议下沉至第 1 层 Rust `core/`**：① 拆出无 JNI 依赖的公共门面 `core/src/engine.rs`，其下分别挂薄插头 `ffi_jni.rs`（Android）与后续 `ffi_c.rs`/UniFFI（iOS）；② 将多箱并发协调器（期望接收端 reconcile、首台建连窗口期加减箱与音量排队、`connecting` 阶段补齐）收进 Rust `Engine`/`CastSession`；③ 发现结果直接输出结构化 JSON 设备模型（含 `kind`/`castable`/`protocol`/`visible_by_default`/`detail`），并统一设备过滤与缓存合并规则；④ 投送路由状态机（本机 ↔ 多接收端互斥、拒绝不可投设备）与认证模式枚举解析下沉至 `core/`；⑤ `stats` JSON 直接输出面向 UI 的归一化字段（单设备 `ui_state` 与 `display_latency_ms`），两端 UI 直接消费渲染。<br>**明确留在第 2/3 层（不下沉）**：Android 的 `MediaProjection`/`AudioPlaybackCapture`/`MediaCodec`/`ForegroundService`/`NotificationListenerService`/`LocalOutputMute`、iOS 的 `ReplayKit`/`AudioToolbox`/`AVAudioSession`，以及各自原生 UI 与本地持久化壳（`SharedPreferences`/`UserDefaults`） |
| **验收条件** | Rust `core/` 新增对应单元测试覆盖引擎门面、并发 reconcile、发现模型/过滤合并、路由状态机与 UI 归一化统计输出；Android 侧 `CastService`/`CastRouteSelection`/`LatencyDisplay` 瘦身为薄适配层且现有 Rust + Android 全部回归单测与 MAR-AL00 多箱投送/重连/延迟验收保持绿色；`core/` 不带 `jni` feature 即可独立编译出面向 iOS 的 `staticlib` 目标（为后续 XCFramework 做好接口冻结） |
| **优先级** | P1（跨端前置架构收口；建议与 #6 配合或在启动 iOS 前完成） |
